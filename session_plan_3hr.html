Lecture + Demo
Set context before any code. Use the "generalist doctor" analogy to make fine-tuning click instantly.
Why Fine-tune? Pre-trained LLM Challenges
Open with the big picture — what pre-trained models can and cannot do, and why fine-tuning exists. Ground every point in a real product example.
What is a Pre-trained LLM?
Explain that GPT-2, Flan-T5, LLaMA were trained on billions of tokens of internet text to learn general language. They are generalists — good at many things, great at few.
Real example
Ask GPT-2 to write a recipe → it generates coherent English but random content, not a recipe format. That's a generalist problem. After fine-tuning on 1,000 recipes → it generates proper ingredient lists and instructions. Show both outputs live.
8 min
Generalization Limits & Task-specific Gaps
Pre-trained models lack domain vocabulary, task format knowledge, and domain-specific reasoning. Show failure cases clearly before showing solutions.
Three failure cases to show
1. Medical: Ask GPT-2 "diagnose from this symptom list" → generic health advice, not clinical reasoning
2. Legal: Ask for a non-disclosure agreement → sounds legal but wrong clauses
3. Code review: Ask for a Python security audit → misses common vulnerabilities
7 min
Fine-tuning: The 3 Core Benefits
Task optimization, resource efficiency, and adaptability. Make the cost argument concrete — it's the most compelling reason for any team to fine-tune vs retrain.
Cost analogy that lands
Training GPT-3 from scratch ≈ $4.6 million, 3 months
Fine-tuning GPT-2 on your domain ≈ $20–$200, one weekend
You're borrowing 1.5B parameters of language knowledge and just teaching the top layers your domain style. Like hiring a smart new grad and giving them 2 weeks of domain training instead of putting them through a full degree.
8 min
Transfer Learning: How Fine-tuning Works Internally
Briefly explain the freeze-lower-layers → adapt-upper-layers pattern. Use the image analogy (edges → shapes → objects) then bridge to text (tokens → grammar → meaning → task).
Visual walkthrough
Layer 1–4 (Frozen): "happy" and "joyful" are similar → general word knowledge
Layer 5–8 (Frozen): subject-verb agreement → general grammar
Layer 9–12 (Fine-tuned): "not happy" = negative sentiment → task-specific reasoning
Only layers 9–12 update during fine-tuning. That's why it's 100× cheaper.
7 min
💬 Quick Poll (end of section)
Ask the room: "Which of these would benefit most from fine-tuning vs just better prompting?"
A) Customer support chatbot   B) General Q&A   C) Code auto-complete for a specific framework   D) Creative writing

Answer: A and C — domain-specific tasks with consistent format. B and D are often solvable with better prompting alone.

Dataset Preparation & Pre-processing
Walk through the complete data pipeline — collection, cleaning, augmentation, tokenization — with hands-on code snippets for each step.
Why Data Quality Beats Everything Else
The "golden rule" of fine-tuning. A clean dataset of 1,000 examples consistently outperforms a noisy dataset of 10,000. Introduce overfitting vs underfitting with concrete scenarios.
Classroom example
Scenario: You're building a movie review sentiment classifier.
Bad data: 8,000 Amazon tech reviews + 2,000 movie reviews. Model learns tech review patterns, fails on movies.
Good data: 1,200 clean, balanced movie reviews. Model learns exactly what you need.
Moral: domain match + cleanliness > volume.

Data Augmentation — Making More from Less
When you have limited labeled data, augmentation creates new training examples without losing semantic meaning. Cover text and image techniques.
Live text augmentation demo

Lecture + Live Experiment
The most technical section. Use the baking analogy first, then go into numbers. The LR experiment is the session highlight — let it run while you explain.
Hyperparameter Optimization
Cover the 6 key hyperparameters with intuitions, then run a live learning rate sensitivity experiment so students see theory become charts in real time.
Learning Rate — The Most Important Dial
How much to update weights after each batch. Too high = overshoots. Too low = never converges. The sweet spot for fine-tuning LLMs is almost always 1e-5 to 5e-5.
Intuition example
Imagine adjusting a thermostat to hit 22°C:
LR = 10 (too high): You jump from 18° → 30° → 14° → 28°. Never stabilizes.
LR = 0.001 (too low): You move 0.001° at a time. Takes forever to reach 22°.
LR = 0.5 (just right): 18° → 20° → 21.5° → 22°. Converges smoothly.

GPT-3 uses LR ≈ 6×10⁻⁵ during pre-training. Fine-tuning typically uses 5×10⁻⁵ or lower.
7 min
Batch Size, Warm-up, Epochs & Optimizers
Cover the remaining 5 hyperparameters concisely with decision rules students can apply immediately.
Decision table
Batch size: 16–32 for fine-tuning. Smaller = noisier updates but better generalization.
Warm-up steps: Set to 5–10% of total steps. Prevents "weight shock" at start of training.
Epochs: 3–5 for fine-tuning. Use early stopping — stop when val loss stops improving.
Optimizer: AdamW for 99% of cases. SGD if dataset is huge and memory is tight.
Frozen layers: Freeze layers 1–8, fine-tune layers 9–12 for most classification tasks.
8 min
Regularization — Preventing Overfitting
Dropout, weight decay, early stopping. Make the concept visceral with a concrete memorization example.
Memorization vs learning
Overfitting analogy: A student who memorizes last year's exact exam questions.
They score 100% on the practice paper but fail on any new question.

Dropout fix: Randomly disable 20% of neurons each training step → forces model to learn robust patterns rather than relying on specific neurons memorizing specific examples.
Weight decay: Penalizes large weights → keeps model "humble" and generalizable.
6 min
Hyperparameter Search Strategies
Grid search, random search, Bayesian optimization, and evolutionary strategies. When to use each and why Bayesian is the professional's choice.
Bayesian vs Grid — concrete contrast
Grid search: Try LR ∈ {0.1, 0.01, 0.001} × batch ∈ {8, 16, 32} = 9 experiments. Exhaustive but ignores past results.

Bayesian: Run experiment 1 (LR=0.1, batch=8) → bad. Run experiment 2 (LR=0.001, batch=32) → good. Bayesian now predicts: "try LR=0.0005, batch=32 next" — learns from history like a detective narrowing suspects.

Tools: Optuna (free, flexible), W&B Sweeps (visual), Ray Tune (distributed).

Lecture + Calculation
Students often confuse BLEU and ROUGE. Do the manual calculation live — once they compute it by hand, they never forget which is which.
Evaluation Metrics — BLEU, ROUGE & Beyond
When output is text, accuracy doesn't apply. Cover the metrics used for generation tasks and walk through manual calculations before using the library.
Classification Metrics Recap
Quick 5-minute recap of Accuracy, Precision, Recall, F1 — set up the contrast with text generation metrics. The medical example makes Precision vs Recall unforgettable.
The Recall vs Precision tradeoff
Cancer screening: Missing a cancer case (false negative) = patient doesn't get treatment = potentially fatal.
→ Optimize for Recall (catch everything, even if some false alarms)

Spam filter: Blocking a legitimate email (false positive) = user misses important message.
→ Optimize for Precision (only block if very confident it's spam)

F1 = when you can't sacrifice either. Use this for most NLP classification tasks.
5 min
BLEU Score — Precision for Text Generation
N-gram precision: how many words/phrases in the generated text appear in the reference? Originally for translation, now used broadly. Walk through the math live.
Manual calculation — do this on whiteboard
Reference: "The cat sat on the mat"
Generated: "The cat is on the mat"

BLEU-1 (unigrams): Generated has 6 words. 5 appear in reference (The, cat, on, the, mat). Precision = 5/6 = 0.833
BLEU-2 (bigrams): Generated bigrams: (The cat), (cat is), (is on), (on the), (the mat). Matching: (The cat), (on the), (the mat) = 3. Precision = 3/5 = 0.600
Final BLEU = geometric mean of BLEU-1, 2, 3, 4 × brevity penalty
8 min
ROUGE Score — Recall for Summarization
Flip side of BLEU: how much of the reference is captured in the generated text? ROUGE-1, ROUGE-2, ROUGE-L. Used in summarization to check content coverage.
Same example, different lens
Reference summary: "The government announced a new climate policy"
Generated summary: "A new government climate policy was revealed"

ROUGE-1 Recall: Reference has 7 words. How many appear in generated? (government, new, climate, policy) = 4. Recall = 4/7 = 0.571
ROUGE-2 Recall: Reference bigrams: (The government), (government announced), (announced a), (a new), (new climate), (climate policy). Matching in generated: (new climate), (climate policy) = 2. Recall = 2/6 = 0.333

Key insight: BLEU = did we say the right words? ROUGE = did we cover the right information?
8 min
Interpreting Scores & Limits of Automatic Metrics
What's a "good" BLEU score? When do these metrics fail? End with a discussion on why human evaluation still matters.
Score interpretation + failure case
BLEU thresholds (roughly): <10 = very poor, 10–20 = decent, 20–40 = good, 40+ = near-human
ROUGE-1 thresholds: <0.3 = poor, 0.3–0.5 = decent, 0.5+ = good

When metrics lie:
Reference: "The dog bit the man." Generated: "The man bit the dog." → BLEU=0.8, ROUGE=0.8. But the meaning is completely reversed!
→ Why human eval, BERTScore, and BLEURT were developed.

Lecture + Architecture Demo
RAG is the most "wow" moment of the session. Lead with the open-book exam analogy, then build the pipeline step by step. Save the live demo for the end.
Retrieval-Augmented Generation (RAG)
Fine-tuning teaches skills. RAG provides knowledge. Together they form the backbone of most production AI applications today. Walk the pipeline end-to-end with a real example.
The Problem RAG Solves
LLMs have three critical weaknesses in enterprise use: knowledge cutoff, hallucination, and no access to private data. RAG solves all three without retraining.
Three failure modes — ask the class these questions live
Q1: "What happened in the news yesterday?"
→ Any LLM: fails (training cutoff). RAG with news feed: succeeds ✓

Q2: "What does our company's Q3 2024 report say about revenue?"
→ Any LLM: hallucinated answer. RAG with your PDF: exact answer with citation ✓

Q3: "Summarize the meeting notes from last Tuesday."
→ Any LLM: "I don't have access to your meeting notes." RAG: retrieves and summarizes ✓
6 min
The RAG Pipeline — 4 Steps
Walk through each step with the AI companies knowledge base as a running example. Make the embedding concept concrete with coordinates.
Step-by-step with real query
Query: "When was ChatGPT launched and how fast did it grow?"

Step 1 — Embed query: Convert to 384-dim vector: [0.23, -0.18, 0.71, ...]
Step 2 — Search FAISS: Find top-3 document vectors closest in space → returns OpenAI documents
Step 3 — Augment prompt: "Based on: [ChatGPT was launched Nov 2022, reached 100M users in 2 months...] Answer: When was ChatGPT launched?"
Step 4 — Generate: Flan-T5 reads the context and produces a grounded, accurate answer
8 min
Vector Embeddings & FAISS — The Core Machinery
Why do we need vectors? Show how semantic similarity works differently from keyword search. FAISS makes it fast at scale.
Keyword search vs semantic search
Query: "How many users does ChatGPT have?"

Keyword search (TF-IDF): Looks for documents containing "ChatGPT" AND "users". Fails if document says "reached 100 million people" (no word "users").

Semantic search (FAISS): Compares the meaning of the query against all documents. "100 million people" is semantically close to "users" → retrieved correctly.

FAISS searches 1 million vectors in <1ms. That's what makes RAG practical in production.
8 min
Fine-tuning + RAG Together — Production Formula
Neither alone is sufficient. The combination gives you style + knowledge — the gold standard architecture.
GitHub Copilot as real-world example
Fine-tuning contribution: Codex (fine-tuned on GitHub code) knows how to write idiomatic Python, follows coding conventions, understands function signatures.

RAG contribution: When you're working in a specific codebase, Copilot retrieves your existing functions, class definitions, and variable names from the open files — it's doing real-time retrieval over your local context.

Result: code suggestions that match both general Python style and your specific project's patterns.

Session Takeaways

01
Data > Model > Hyperparameters
Clean, domain-matched data at 1,000 examples beats noisy data at 10,000 every time. Invest here first.
02
LR=5e-5 is the default start
For fine-tuning any transformer, start at 5e-5 with warmup. Adjust from there based on validation loss.
03
BLEU = precision, ROUGE = recall
Use BLEU for translation tasks, ROUGE for summarization. Always pair quantitative scores with qualitative examples.
04
RAG for knowledge, Fine-tuning for style
Don't choose — combine them. Fine-tune for domain format + RAG for live factual grounding = production-ready AI.
05
Freeze lower layers, tune upper layers
Lower layers capture universal language patterns. Upper layers are task-specific. Fine-tuning cost comes from updating only the upper ~30% of parameters.
06
FAISS = semantic Google for your docs
Vector similarity search finds the meaning-closest documents, not just keyword matches. This is what makes RAG far superior to simple search.
